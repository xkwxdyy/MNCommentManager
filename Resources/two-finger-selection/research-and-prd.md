# iPad 双指多选调研与优化方案

2026-10-11 调研，2026-10-12 实施。状态：用户已确认方案，正式源码已接入，真实设备待验收。环境依据：用户反馈 iPad 双指多选只有部分尝试成功；宿主为 MarginNote TestFlight 4.5.0 build60。当前源码基线为 `f0cf419031a19e7fabca5d8181ba3add4284b3dc`，手势及模块功能包含未提交改动。本报告不把历史 Chromium 模拟结果视为 iPad 验收。实施和测试包说明见 [validation.md](./validation.md)。

## 问题与本地证据

现有 `web/src/lib/twoFingerSelection.mjs` 已在触摸开始之前注册捕获阶段的非被动监听，并在合格的双指开始事件中立即调用 `preventDefault()`。注册时机不是当前源码中已经证实的缺陷。

现有实现存在可重复的识别和计算问题：

| 诊断轨迹 | 当前结果 | 直接原因 |
| --- | --- | --- |
| 已识别纵向平移后，中点累计移动 170 像素，两指间距从 60 增至 78 像素 | 多选取消，恢复原选区 | 间距变化超过固定 12 像素阈值即判定捏合，未比较共同平移与相对运动 |
| 两指中点位于 15 像素评论间隙 | 无法开始 | 命中规则只接受评论矩形内部，间隙返回空值 |
| 触点位于正文链接 | 无法开始 | 所有链接均被归为禁止手势的交互元素 |
| 起始横移 13 像素、纵移 10 像素，随后转为纵向 | 无法恢复识别 | 初次横向占优即永久取消，直到全部抬手 |
| 同一条评论内、动画帧执行前收到 300 次移动 | 300 次选区提交、301 次命中查询 | 没有按帧合并，也没有跳过不变终点 |
| 手势在列表中部停留，模拟执行 120 帧 | 继续申请帧并读取容器矩形 120 次 | 非边缘位置仍持续运行动画循环 |

调研时的诊断代码为 [diagnose-current.mjs](./diagnose-current.mjs)，改动前的原始结果为 [current-diagnostics.json](./current-diagnostics.json)。该脚本导入工作区中的手势模块，优化后重新运行会采用新实现；历史结果以已保存的 JSON 为准。轨迹由脚本合成，证明当时的判定和调用次数；轨迹不是实际手指采样，不证明设备上的识别率或帧率。

正式 React 钩子在每次命中时新建可见索引集合，并逐个读取评论矩形。选区变化还会重新执行 `App.jsx` 中的评论映射，重新计算媒体、链接及模块控制状态。源码证实重复工作存在；各环节对 iPad 耗时的贡献仍需性能采样确认。

开源代码比较支持以下判断：现有模块继续保留范围选择契约，通过独立实现吸收识别、按帧更新和位置缓存思路，比直接替换成通用框选库更符合当前结构。该判断属于本项目的方案推导，不是开源项目对 MarginNote 的兼容性承诺。

## 网页手势约束

[W3C Touch Events](https://www.w3.org/TR/touch-events/#the-touchstart-event)规定取消触摸开始或首个移动事件与默认滚动之间的关系。当前方案继续预先注册非被动监听，单指触摸不调用 `preventDefault()`；合格双指候选立即阻止默认处理，避免等待到产生选区后再尝试接管。

[W3C Pointer Events](https://www.w3.org/TR/pointerevents3/#determining-supported-direct-manipulation-behavior)明确：浏览器已开始平移或缩放后，本轮操作中的 `touch-action` 修改会被忽略；多个并发触点的处理方式也不由该节统一规定。因此，临时修改 CSS、改用 Pointer Events 或 Pointer Capture 都不能保证收回已经交给系统的滚动。先用单指启动滚动，再放下第二根手指的操作，需要保留安全失败规则。

网页识别器无法保证与 UIKit 完全等同。正常双指进入时的可靠性、自然移动容差及渲染开销可以优化；系统已经接管的输入必须与源码缺陷区分。

## 简要产品需求文档

### 问题

正常双指纵向移动容易被起点命中、早期方向或间距变化拒绝；移动事件重复触发布局查询和选区更新。自动测试原先集中在理想触点轨迹，对自然偏移、异步触点和更新次数缺少覆盖。

### 成功标准

- 正文、正文普通链接和评论之间的窄间隙可以开始双指范围选择；操作按钮、输入区、原生摘录和模块标题保持各自语义。
- 同向移动伴随轻微间距变化不会恢复原选区；明确捏合在多选识别前退出，已进入多选后保持该模式至抬手或真实中断。
- 反向拖动按开始前的选区回缩；筛选隐藏项、模块隐藏项及原生摘录不被范围选择误改。外部选区操作继续具有优先级。
- 同一动画帧最多提交一次移动更新；相同终点不提交选区；列表中部静止时没有持续动画循环；抬手前尚未执行的最后一帧被同步处理。
- 单指原生滚动、正文单指链接点击和键盘操作继续通过；移动、删除等按钮不被双指误触发。
- iPad 真机验收目标：正常双指启动及不超过 120 毫秒的先后接触测试合计 40 次，成功率至少 95%；首个高亮在达到识别条件后 80 毫秒内出现。已经开始的单指滚动、系统中断和禁止操作区单独记录，不混入该识别率。
- 使用 500 条混合评论验证，记录动画帧及识别到渲染的延迟；手势计算每帧第 95 百分位耗时以 4 毫秒为目标，超过目标则继续优化。设备实际指标待采样，不能用桌面测试结果替代。

上述时间和比例属于待确认的验收目标，不是当前性能测量结果。真实设备测试需记录设备型号、系统版本、宿主版本、显示刷新率、轨迹类别、成功次数及原始时序。

### 范围与约束

实施范围为共用双指手势模块、正式 React 钩子、必要的评论渲染缓存、共用演示与验证脚本。保留现有选择、回缩、中断恢复和外部选区优先规则。新增验证覆盖真实移动变形和事件吞吐量。

业务数据及宿主写入接口不变；拖动过程中不调用 Bridge。不更换整页为原生列表，不对整个评论区域设置 `touch-action: none`，不增加框选库依赖，不复制外部许可证受限源码。现有未提交改动继续保留。本阶段不提交、推送或发布。

### 初步方案

1. 为双指候选分别记录触点起点和位移；综合共同位移、相对位移、方向一致性判定，增加短暂的歧义容忍。起始位移先采用 8 像素候选值，通过测试调整；不会仅放宽旧间距阈值。完成识别后锁定多选模式，保留额外触点、失焦、系统取消和外部选区更新的中断处理。
2. 触点始终按 identifier 配对。允许评论正文普通链接参与候选；按钮和输入区仍拒绝进入，避免既有按住删除或移动操作与多选冲突。窄间隙采用邻近可见评论，模块标题、原生摘录和大段空白不作为邻近评论的入口。
3. 在手势开始时建立按纵向排列的评论位置快照，以内容坐标和二分查找命中；滚动只补偿实际偏移。列表重排、容器变尺寸、图片加载和正文尺寸变化使快照失效，在下一次需要命中时重建，避免每个触摸事件逐项测量。
4. 触摸移动先执行识别和必要的 `preventDefault()`，记录最新位置；动画帧合并命中和选区提交，跳过不变终点，按前后范围差异更新。抬手必须处理最后位置，中断必须取消待处理更新。
5. 边缘滚动沿用按经过时间计算速度的方式，优化边缘渐进曲线，按实际滚动量推进选区。中部不运行连续动画，达到滚动边界后停止空转，重新靠近有效边缘时恢复。
6. 首先减少不必要的 React 更新；对内容派生计算和重型评论正文做有针对性的缓存，确保双指触摸节点持续连接。只有性能证据仍显示渲染超出预算时，才进一步拆分选区订阅；不先改造全局状态架构。

### 验证与实施顺序

先用合成触摸轨迹固定识别问题和调用次数，再修改识别与调度；随后接入位置缓存和必要的渲染缓存，复验现有 #59、#60 的中断及选区规则。浏览器检查使用可信多点触摸覆盖先后接触、对角启动、间距变化、链接、间隙、回缩、边缘滚动及长列表，最后从隔离构建产生测试包。

Chromium 与 JSDOM 只证明相应环境中的逻辑和性能。iPad MarginNote WebView 的自然手势及系统接管行为必须单独验收；测试包交付时明确待验收项目，Issue 保持开放。

### 待解决问题

用户已明确确认实施方向。双指先后接触但首指已经引发系统滚动的情况能否进一步改善，取决于真实 WebView 的事件顺序；本阶段提供可复查的诊断记录，不承诺网页层能够收回系统手势。若真实设备仍持续出现系统提前接管，再单独调查宿主原生识别接口，按原生 API 文档确认可用能力后提出后续方案。
